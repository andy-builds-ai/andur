# Architecture

Svar is a chatbot: it answers questions from a company's own documents, and
says where each answer came from. It is one part of a larger system called
Andur. The second part, the agent Vard, is in neither stack yet (`vard/`,
[README](../vard/README.md)).

It is shown with made-up companies. Each has its handbooks, policies and
notes in a folder, and Andur keeps each company's documents in a workspace
of their own. Whoever holds the workspace's key can ask Svar in plain
language instead of searching. Every answer carries its sources, and every
source says which layer it came from: written by a person, produced by a
machine, or merely arrived and not yet sorted. One deployment serves several
companies. Every search is filtered to the asking workspace, and the handler
drops any passage of another workspace before the prompt is built. A test on
11.11.2026 found none in the search results of another workspace
([README](../svar/README.md#privacy-and-separation)).

Runs entirely on AWS, defined as code. `cdk deploy --all` builds two stacks,
Taug's `TaugStack` first, then Svar's `AndurStack`. `cdk destroy --all`
removes them except the documents bucket, which stays. Keys and
documents are added afterwards with the scripts
([README](../README.md#build-and-test-it)).

## The parts

| Part | Service | Job |
|---|---|---|
| Documents | S3 | The source of truth. One prefix per workspace, versioned, closed to the public. |
| Vector store | S3 Vectors | Holds the embeddings. Nothing runs while nobody asks, so an idle month costs cents. |
| Retrieval | Bedrock Knowledge Base | Chunking, embedding, search. Managed, so there is no index code to maintain. |
| Embeddings | Titan Text Embeddings V2 | Turns text into the 1024-dimension vectors the index stores. |
| Separation | Metadata filter | `workspace` on every chunk. The filter, not a separate deployment, is what keeps companies apart. |
| Answering | Bedrock behind a Lambda function: Qwen3 235B in the region | Answers from the retrieved passages only and cites them. No idle cost; the function only runs while a question is in flight. |
| Access | One key per workspace | The key decides the workspace. Keys are generated by `taug/scripts/workspace.py`, not by the deploy, and kept as SecureString parameters, which cost nothing. |
| Budget | DynamoDB, one item per key | A key is an allowance, not a password: a demo key has 10 questions and 48 hours from the first one, a key on a plan a quota per month and per day. Billed per request, so an idle month costs nothing. |
| Guardrail | Bedrock Guardrails, on the model call and on the excerpts; gpt-oss-120b in the region for the topics | Refuses legal, tax and medical advice and questions about people, masks personal details in the answer and in the excerpts of its sources, withholds an answer the passages do not carry. Billed per text unit read, or per token for the topic model; nothing while idle. |
| Page | A layer of the answer function | Five files, no framework, nothing loaded from another server. |
| The way in | The answer function's own URL | One https address for the page and for questions. |

The stacks have no OpenSearch cluster, no NAT gateway, no container service
and nothing else with a monthly base fee. Idle, they cost cents
([README](../svar/README.md#cost-measured)).

## One address for everything

There is no CloudFront, since CloudFront cannot be kept to Germany: the
answer function's URL is the one address, open to callers (`AuthType NONE`),
and the function serves the page itself from a layer and sets security
headers on every response (`svar/app/page.py`;
[decisions.md](decisions.md#2026-10-07-frankfurt-function-url)). The
workspace key, its workspace and its budget are checked in the function on
every call.

That shape buys two things. The page calls `/ask` as a relative path, so it
never has to know its own address and there is no configuration file to keep
in step. Page and function share an origin, so there is no cross-origin
request and nothing to allow with CORS.

The key travels in a header of its own, `X-Andur-Key`, as in the curl
examples in [operating.md](operating.md#with-curl). The function may run 195
seconds; how a question fits in them is in the
[app README](../svar/app/README.md). The median time per question, measured
from a laptop in Germany, is a few seconds
([README](../svar/README.md#measured)).

## What the stacks create

`infra/app.py` builds two stacks in one account and region. Taug's,
`TaugStack` (`taug/infra/stack.py`), creates the documents bucket, the
vector bucket and index, the knowledge base with its service role, and a data
source pointing at the documents.
Svar's, `AndurStack` (`svar/infra/stack.py`), depends on it and imports the
knowledge base's id and ARN. It creates the table that
holds each key's budget, the guardrails (on the answer and on the excerpts of
its sources), the answer function, and the layer it serves the page from at
its own URL. The answer function packs
Taug's access library (`taug/access/`: the key check and the workspace
rules) next to its own code. A fill script loads a demo
corpus of two fictional companies into Taug's, a retrieve script shows that a
query in one company's workspace never returns the other's documents, and an
ask script puts a question to the deployed address. The page itself is five
files in `svar/web/`: no framework, no build step, nothing from another server.

Every key carries a budget. A demo key has ten questions, and 48 hours from
the first of them; a key on a plan gets a quota from `svar/app/plans.py`, per
German calendar month and per day, that renews itself. The handler counts a
question against the key that asked before it
retrieves anything, in a conditional write against a DynamoDB item found by
the SHA-256 of the key: one for a demo key, and for a key on a plan a
second after the first has refused it and handed back the plan. A demo key
with nothing left gets a 402 that says which half ran out; a key on a plan
whose quota is full gets a 429 that says whether it is the month's or the
day's. The demo's numbers can be set per key without a deploy, and
`python -m taug.scripts.workspace plan` changes a key's plan; how both work is
in [svar/app/README.md](../svar/app/README.md).

Every question is checked before the model is asked: gpt-oss-120b in the
region refuses legal, tax and medical advice and questions about people's
private lives, reading the question after "Customer to business: ", since
read alone, harmless questions about an invoice were refused as tax
questions. Every answer passes a guardrail on the same model call that masks
names, e-mail addresses, phone numbers and addresses in it and withholds it
if the retrieved passages do not carry it. The answer itself, without its
citations, is checked by gpt-oss-120b again, which withholds it if it
strays into one of the same four topics: with the citations, short harmless
answers were withheld for them alone. The excerpts of the sources pass a
second guardrail that masks the same details. A refused question, and an
answer withheld for one of the four topics, come back without sources. No
guardrail checks the topics: the tier that reads German would carry the
check out of Germany.

The masking is statistical, not a list of names, and it misses: a first
name without a surname can slip through
([decisions.md](decisions.md#2026-09-23-masking-is-a-filter)). Treat the
masking as a filter that catches most personal details, not as a guarantee;
documents that must not show a name to a reader must not hold it. Every answer also
carries its cost in USD, with the day its prices were read. Both are in
[svar/app/README.md](../svar/app/README.md#the-guardrail).

## Build steps

1. **Infrastructure:** documents bucket, vector index, knowledge base, IAM.
   *(done)*
2. **Ingest:** a fill script and a demo corpus of two made-up companies, 37
   Markdown documents uploaded as 147 sections. *(done)*
3. **Answering:** a Lambda handler with one key per workspace: question,
   retrieval, model, answer with sources and layer, token counts per answer
   in the log. *(done)*
4. **Key budgets:** a key is an allowance, ten questions and 48 hours,
   counted in DynamoDB. *(done)* A key can carry a plan, a quota per month
   and per day. *(done; the first key on a plan was set up in eu-central-1
   on 07.10.2026)*
5. **The page:** served by the answer function at its own URL. *(done)*
6. **Guardrails:** topic, masking and grounding checks, and the cost of every
   answer in its log line. gpt-oss-120b in the region checks the denied
   topics. *(done)*
7. **One region:** Frankfurt (`eu-central-1`), where Svar runs; the code
   builds it alone since 18.11.2026 ([decisions.md](decisions.md)).
   What runs where is in [status.md](status.md). *(done)*
8. **Measurements:** `evaluate`, `control_eval`, `topic_probe`,
   `grounding_probe` and `rehearsal` against the deployed stacks
   ([README](../svar/README.md#measured); the dates in
   [status.md](status.md#last-measured)). *(done)*
9. **Vard:** his loop and the receiving check, measured with eleven models on
   twelve made-up cases on 20.10.2026. Not deployed
   ([README](../vard/README.md)). *(first build done; the second picked his
   model on 24 made-up cases on 21.10.2026, MiniMax M2.5; nothing is
   deployed)*
10. **Release:** screenshots and a walkthrough *(done)*. There is no tagged
    version.
11. **Taug's stack of its own:** `TaugStack` holds the documents, the vectors
    and the knowledge base, and Svar's `AndurStack` imports the knowledge base
    from it ([decisions.md, 10.11.2026](decisions.md#2026-11-10-taug-stack-of-its-own)).
    *(done in Frankfurt, [status.md](status.md))*
